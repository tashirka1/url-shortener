## ДОБАВЛЕННЫЕ Требования

### Требование: Пользователь может создать API-токен
Система ДОЛЖНА позволять авторизованным пользователям создавать новый API-токен с человекочитаемым именем.

#### Сценарий: Успешное создание токена
- **КОГДА** пользователь отправляет форму создания токена с именем
- **ТОГДА** система генерирует криптостойкий случайный токен, сохраняет его SHA-256 хеш в таблицу `api_token` и показывает сырой токен ровно один раз

#### Сценарий: Валидация имени токена
- **КОГДА** пользователь отправляет пустое имя или имя длиннее 128 символов
- **ТОГДА** система возвращает ошибку валидации и не создаёт токен

### Требование: Пользователь может просматривать API-токены
Система ДОЛЖНА отображать все активные API-токены пользователя с именем, префиксом (первые 8 символов) и датой последнего использования.

#### Сценарий: Список токенов в дашборде
- **КОГДА** пользователь переходит на страницу API-токенов
- **ТОГДА** система рендерит таблицу всех неотозванных токенов, отсортированных по дате создания по убыванию

### Требование: Пользователь может отозвать API-токен
Система ДОЛЖНА позволять пользователю отозвать API-токен по ID, делая его навсегда недействительным.

#### Сценарий: Успешный отзыв
- **КОГДА** пользователь нажимает «Отозвать» на токене
- **ТОГДА** система устанавливает timestamp `revoked_at` и токен больше не может авторизовывать API-запросы

#### Сценарий: Отзыв несуществующего токена
- **КОГДА** пользователь пытается отозвать токен с ID, который не существует или принадлежит другому пользователю
- **ТОГДА** система возвращает ошибку

### Требование: Токен хранится только в виде хеша
Система НЕ ДОЛЖНА хранить сырой токен в базе данных. Только SHA-256 хеш.

#### Сценарий: Хранение хеша токена
- **КОГДА** токен создаётся
- **ТОГДА** в `api_token.token_hash` сохраняется только SHA-256 хеш (hex-кодированный) полного токена
