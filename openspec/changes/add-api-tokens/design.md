## Контекст

Сейчас приложение поддерживает только cookie-сессионную авторизацию (gorilla/sessions). Вся работа со ссылками идёт через htmx-ориентированные HTML-обработчики, которые вызывают существующий `link/service.LinkService`. Для программного доступа нужна токен-авторизация и JSON API, переиспользующие тот же слой сервисов.

## Цели / Не-цели

**Цели:**
- Дать пользователям возможность генерировать и отзывать API-токены через веб-интерфейс
- Авторизовывать API-запросы через заголовок `Authorization: Bearer <token>`
- Предоставить REST-эндпоинты для основных операций со ссылками: создать, список, удалить, статистика
- Переиспользовать существующие `link/service` интерфейсы — никакой дублирующейся бизнес-логики
- Минимум нового кода — опираться на существующие сервисные интерфейсы

**Не-цели:**
- Нет API-эндпоинтов для регистрации или управления пользователями
- Нет OAuth2 / OIDC — только простые bearer-токены
- Нот отдельного rate limiting для API-токенов (переиспользовать существующую middleware)
- Нет гранулированных прав — токен имеет полный доступ к ссылкам владельца

## Решения

1. **Формат токена: `sk_` + 44 символа base62** — 32 байта из `crypto/rand`, base62-кодирование даёт ~256 бит энтропии. Префикс `sk_` делает токены визуально узнаваемыми. В БД хранится SHA-256 хеш; сырой токен показывается только один раз при создании. Это подход «API-ключ как пароль».

2. **Новый модуль `internal/apitoken/`** — следует существующей плоской модульной структуре (model, storage, service, handler, views). Изолирует ответственность, консистентно с `auth/` и `link/`.

3. **API-прослойка в `internal/core/api/`** — компактная middleware, читающая заголовок `Authorization`, хеширующая токен, находящая пользователя в таблице `api_token` и устанавливающая ID пользователя в контексте Echo через `c.Set("userId", id)`. Это проще, чем модифицировать существующую session-middleware.

4. **API-обработчики — отдельные функции, а не новый модуль** — это тонкие обёртки: парсинг JSON-запроса → вызов существующего `link.Service` → JSON-ответ. Живут в `internal/link/handler/api.go`, рядом с пакетом link handler. Новые templ/views для API не нужны.

5. **Управление токенами в дашборде** — доступно через новый раздел «API-токены» на странице дашборда (`GET /link/tokens`). Использует тот же htmx-паттерн для инлайн-создания/отзыва. Форма PicoCSS для создания токена (поле имени + кнопка отправки), таблица существующих токенов, кнопка отзыва у каждой строки.

## Риски / Компромиссы

- [**Безопасность**] Токен показывается один раз → пользователь должен скопировать его сразу. Смягчение: кнопка «Копировать» с JS-запасным вариантом и предупреждение.
- [**Миграция**] Добавление API-пути авторизации увеличивает поверхность атаки. Смягчение: минимальная middleware (<30 строк), строгая валидация, сравнение хеша через `subtle.ConstantTimeCompare`.
- [**UX**] Если пользователь потеряет токен, придётся отозвать и создать новый. Смягчение: чёткое сообщение в интерфейсе.
