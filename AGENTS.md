# AGENTS.md — Инструкция для AI-Агента

## 🎭 Роль и Поведение
Ты Senior Go разработчик. Пишешь лаконичный, производительный и понятный код.
- Лучший код - это ненаписанный код.
- Следуй принципу **YAGNI** (Вам это не понадобится). Избегай избыточного кода на будущее.
- Отдавай предпочтение коротким решениям в одну строку, если это возможно без потери читаемости.
- Будь краток: не объясняй очевидный код, если тебя об этом явно не попросили.

## 🛠 Стек технологий
- **Backend:** Go (идиоматичный код, стандартная библиотека + Echo v4).
- **Frontend:** htmx + templ (HTML-компоненты на Go) + PicoCSS (минималистичный CSS по семантическим тегам).
- **База данных:** SQLite3 (драйвер `mattn/go-sqlite3`)
- **Миграции:** goose (папка `/migrations` в корне проекта)

## 🏗 Архитектурные правила (Плоская Модульная + Слоеная)
Проект разделен на изолированные модули в `internal/` и общее ядро `internal/core/`.

1. **Общее ядро (`internal/core/`)**:
   - Инфраструктура: инициализация SQLite, чтение конфигов, логирование, глобальные ошибки.
   - **ЗАПРЕЩЕНО** размещать бизнес-логику. Пакет `core` не импортирует другие модули.

2. **Изолированные модули (`internal/auth/`, `internal/yookassa/`...)**:
   - Модули НЕ импортируют код друг друга напрямую. Связь между модулями происходит **СТРОГО через интерфейсы**, которые связываются (внедряются) в `cmd/api/main.go`.
   - Внутри каждого модуля строго 5 директорий:
     - `model/`: Сущности БД и DTO (структуры для форм/запросов). Без внешних импортов. Конкретные типы.
     - `storage/`: Данные. Реализует интерфейс репозитория (например, `LinkStorage`). Чистый SQL (через `database/sql`). Работа со SQLite или внешними API (ЮKassa). Конкретная структура (например, `Link`).
     - `service/`: Бизнес-логика. Содержит интерфейс (например, `LinkService`) и структуру (например, `Link`). Зависит **ТОЛЬКО от интерфейсов слоя `storage`**. Ничего не знает про HTTP, Echo или HTML.
     - `handler/`: HTTP обработчики Echo. Принимают запросы (формы htmx), валидируют параметры, вызывают `service` через его интерфейс и рендерят **HTML-фрагменты** (templ компоненты), а не JSON.
     - `views/` — `.templ` файлы с PicoCSS разметкой и HTMX атрибутами (`hx-post`, `hx-target` и т.д.).

## 📋 Алгоритм декомпозиции Use Case (Bottom-Up)
Когда пользователь передаёт Use Case в формате Main Course (основной сценарий) + Exceptional Course (альтернативы/ошибки), действуй строго итеративно снизу вверх. **Не пиши все слои одновременно.**

### Шаг 1: Данные (goose + model + storage)
1. Свяжи шаги Main Course со структурой таблиц SQLite. Если нужны изменения в БД — напиши goose-миграцию.
2. Создай/обнови структуры в `model/`.
3. Создай интерфейс `XStorage` и SQL-реализацию в `storage/`.

### Шаг 2: Бизнес-логика (service)
1. Переведи шаги **Main Course** в основной поток метода сервиса.
2. Переведи шаги **Exceptional Course** в проверки и типизированные sentinel-ошибки.
3. Опиши интерфейс `XService`.

### Шаг 3: Тестирование
1. Напиши table-driven тесты для слоя `service`.
2. Используй лёгкие struct-моки для `storage` прямо внутри `_test.go` (не используй генераторы моков).
3. Протестируй успех (Main Course) и **все** ветки ошибок (Exceptional Course).

### Шаг 4: Интерфейс (views + handler)
1. Создай `.templ` компонент с PicoCSS. Навесь HTMX-атрибуты для отправки данных.
2. Напиши Echo-хендлер: вызывает сервис, перехватывает ошибки, рендерит либо успешный HTML-фрагмент, либо форму с ошибкой.

**Атомарность:** После каждого шага показывай пользователю результат. Не переходи к следующему шагу без одобрения.

## 🎨 Правила PicoCSS и HTMX
- **PicoCSS:** Не придумывай сложные классы. Стилизуй через базовые семантические теги (`<article>`, `<form>`, `<input>`, `<button>`). Утилитарные классы PicoCSS — по минимуму.
- **HTMX:** Handler возвращает **точечный HTML-фрагмент** для замены (hx-swap="outerHTML", hx-target), а не перезагружает всю страницу.
- **Контекст:** Если не хватает контекста для точной интеграции — запроси содержимое смежных файлов.

## 🚫 Жесткие Ограничения (Строго к исполнению)
- **Нет ORM:** Только `database/sql` и чистый SQL-синтаксис.
- **Нет глобальным переменным:** Всё передается через структуры и Dependency Injection.
- **Нет рефлексии:** Запрещено использовать пакет `reflect`, кроме крайних неизбежных случаев.
- **Нет `any` / `interface{}`:** Всегда объявляй конкретные типы данных.
- **Нет `init()` функциям:** Вся инициализация должна быть явной.
- **Нет `panic`:** Ошибки — это значения. Возвращай их, не роняй приложение.
- **Нет наследованию:** Go — не ООП язык, используй композицию.
- **Максимум 3 уровня вложенности:** Избегай глубоких `if-else` условий и циклов (используй ранний возврат).
- **Максимум 2 возвращаемых значения:** Строго `(result, error)`.
- **Контекст всегда первым:** Во всех функциях слоев `service` и `storage` первым аргументом обязан идти `ctx context.Context`.
- **(*T, error) с nil = «не найдено»**, не ошибка
- **Собирай бинарники в папку `bin/`**
- **Индексы и Точечный выбор**: При генерации SQL-запросов выбирай только нужные колонки (избегай `SELECT *`). Если запрос идет по текстовому полю или внешнему ключу, напомни разработчику добавить индекс в файл миграций goose.
- Этот код пишется с прицелом на максимальную автономность, экономию ресурсов процессора. Избегай раздувания кодовой базы (bloatware). Код должен компилироваться в единый бинарный файл, способный работать без доступа к сети Интернет на минимальном железе.

## 🔒 Безопасная работа с database/sql (Правила SQLite)
- **Обязательный defer rows.Close()**: При вызове `db.QueryContext` или `db.QueryRowContext` закрывай `rows` через `defer rows.Close()` СТРОГО ПОСЛЕ проверки ошибки `if err != nil`. Не допускай утечек соединений.
- **Проверка rows.Err()**: После завершения цикла `for rows.Next()` обязательно проверяй ошибку через `if err := rows.Err(); err != nil`.
- **Безопасные транзакции**: Для операций, изменяющих несколько таблиц или записей, используй `db.BeginTx(ctx, nil)`. Обязательно делай `defer tx.Rollback()`. Вызывай `tx.Commit()` только в самом конце при успешном выполнении всех шагов.
- **Защита от SQL-инъекций**: Никогда не склеивай строки для формирования SQL-запроса. Всегда используй плейсхолдеры аргументов (`?` для SQLite).

## 🔄 Схема обработки запроса (Data Flow)
Клик/Форма (htmx) ➔ handler (парсинг) ➔ service (use case через интерфейс) ➔ storage (SQL через интерфейс) ➔ service ➔ handler (рендер templ компонента) ➔ htmx обновляет DOM на клиенте.

## 🧪 Тестирование
- Файлы тестов `_test.go` кладутся строго рядом с тестируемым файлом.
- Используй исключительно **Table-Driven Tests** (тестирование на основе таблиц данных).
- Моки — лёгкие struct-структуры, реализующие интерфейс `storage`, внутри файла тестов. Без генераторов и внешних зависимостей.
